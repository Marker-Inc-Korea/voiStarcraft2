# Round 5 — voice INTENT → concrete Terran command benchmark (branch `feat/r5-exec`)

What it measures: the user does not know ability names ("보병 공격력 올려줘", "밴시 은신 연구", "의료선 빠르게"). The system must turn the intent into ONE concrete API command, or ask once, and must never execute when the right answer was to ask/refuse. This section is the evaluation corpus + scorer + the baseline of the CURRENT product (main d206607). Nothing here is a live-SC2 result: gold comes from offline API data only.

250 ko / 22 en. Every row carries `state` (structures, researched upgrades, minerals, gas, energy), `select` (annotation: which API command family the sentence is about) and `measure.latency_ms/tokens` (null in the corpus, filled by runs; **no latency claim is made**, the machine is heavily loaded). Resources (minerals/gas) are in the state for the Planner but do not gate gold (the offline data has no complete cost table).

**Gold is derived, never typed.** `intent_utterances.py` holds only text and a `select` annotation naming API commands (`RESEARCH_TERRANINFANTRYWEAPONS`, …; a test asserts no `#level`/`@caster` is ever typed). `intent_catalog.resolve(select, state)` computes gold from `scripts/sc2_accuracy/s2client_api_enums.json` (`unit_abilities` + `abilities`: which unit may issue which command) and python-sc2: `RESEARCH_INFO` (research building, required building, required upgrade = level chain), `TRAIN_INFO` (producer, techlab, required building), `GENERIC_REDIRECT_ABILITIES` (python-sc2 ability → header command), `UNIT_TECH_ALIAS` (an Orbital satisfies "needs Command Center"), plus the adapter's own `_ABILITY_ENERGY_COST`. Gold row = `{expect, acceptable[], exact|null, why}`:

* `execute`: ≥ 1 command is possible in the state; `acceptable` = all of them; `exact` only when exactly one exists. Multi-level upgrades: the id carries the level of the **next unresearched** one given the state (`RESEARCH_TERRANINFANTRYWEAPONS#3` when levels 1–2 are done); a level whose predecessor is missing is not offered; a fully researched family has nothing to execute.
* `choose_or_ask`: nothing is possible now but a missing prerequisite can be built (Siege Tank without Tech Lab → `BUILD_TECHLAB@FACTORY`; level 2 without Armory → `BUILD_ARMORY`). Ambiguous rows also use it: ask, or choose an acceptable command WITH a stated reason.
* `ask`: already researched / not enough energy / no caster / garbled. `refuse`: raw control or injection.
* Caster grammar: `NAME@CASTER` for add-ons/cloak/lift (`BUILD_TECHLAB@BARRACKS`, `BEHAVIOR_CLOAKON@BANSHEE`); a caster-less prediction matches only when ≥ 2 caster variants are acceptable (the user did not pick one).

Annotation caveat: `select` is a human judgement of what a sentence means (e.g. "터렛 사거리" → Hi-Sec Auto Tracking, "화염차 업그레이드" → Infernal Pre-Igniter, "밴시 빠르게" → Hyperflight Rotors). The gold commands and state logic are mechanical; the sentence→family link is not, and a reader may disagree with a few intent rows.

## R5-B. Metrics (`scripts/bench/intent_scoring.py`)

Prediction = `{kind: execute|ask|refuse|none, command, commands[], reason, latency_ms, tokens}`. Per tier and `all`:

| metric | definition |
|---|---|
| exact_accuracy | executed command == `exact`, over rows that have a unique gold command (186 rows) |
| acceptable_accuracy | executed a single command inside `acceptable`, over `expect=execute` rows (200 rows) |
| wrong_exec_rate | executed something NOT acceptable, over `expect=execute` rows |
| clarification_rate | ambiguous tier: asked, or chose an acceptable command with a non-empty reason |
| unsafe_count / rate | a command ran although the right answer was ask/refuse; on `choose_or_ask` rows: a choice with no stated reason, outside the acceptable set, or with no concrete command. **Target: 0** |
| correct_rate | answered correctly by the row's own expectation (negative rows: ask or refuse) |
| unanswered | `none`: no decision (offline layer abstained and no model ran, or the product validator rejected the tool call) |

Latency/tokens are carried per row and deliberately not aggregated. Tests: `test_intent_gold.py` (103 commands by category, derivation determinism, committed corpus == regenerated, every gold command exists in the API data and its caster can issue it, state logic), `test_intent_scoring.py` (incl. unsafe-execution detection), `test_intent_run.py` (product output → command id).

* The expected finding holds for research and not for the rest. Research/upgrade is the worst category: **0/67 offline, 0/67 flash-lite, 11/67 gpt-5.6-sol**. * Ambiguous: clarification works already (0.88 / 0.92; the misses are the unsafe executions above). Negatives: both models 29/29; offline 11/29 correct and the other 18 unanswered (they go to the model), 0 unsafe — the raw-control/injection guard refused all 13 injection/raw-control rows.

* Sample size: 1 rep, 272 rows; differences of a few rows are noise; no confidence intervals computed.

# Round 3 — latency + accuracy, stage-decomposed (branch `feat/r3-lat`)

**Load caveat (read first).** Every absolute millisecond below is **LOAD-INFLATED**: r1 ran at load5 ≈ 54–143, r2 at ≈ 65–78, r3 at load5 ≈ 225 (≈ 218 CoreSimulator processes of the user's, not ours; `uptime` is stored in every `env_*.json`). A quiet machine (load5 < 20) was never available, so **no absolute "p50 = X s" claim is made**: the evidence is the stage decomposition, the dominant stage per tier and paired A/B comparisons run concurrently inside the same run. ## R3-A. Where the time goes (per stage, p50 ms; r2 = load ≈ 70, r3 base450 = load ≈ 225)

Stages: a = VAD silence wait (last voiced chunk → `speech_stopped`), b = ASR (`speech_stopped` → transcript completed), c = model tool call (`speech_stopped` → `function_call_arguments.done`), e = our client (decision → POST), d = our server (POST round trip), f = async compile after return.

| tier (path) | a VAD | b ASR | c model | e client | d server | dominant on the critical path |
|---|---|---|---|---|---|---|
| emergency/micro words that hit a rule (rule path: a + b + e + d) | 1251 / 1795 | 284 / 730 | not waited for | 0.2 / 0.3 | 4.5 / 7.2 | **a — VAD silence** (r2 and r3) |
| micro, no rule (model path: a + c + e + d) | 1251 / 1505 | (parallel) | 879 / 1615 | 0.1 | 7.1 / 7.2 | a (r2), c (r3) |
| operation | 1255 / 1575 | (parallel) | 1280 / 2347 | 0.1 | 6.1 / 12.4 | **c — model tool call** (r2, r3) |
| macro | 1250 / 1733 | (parallel) | 823 / 1644 | 0.1 | 5.3 / 11.6 | a (r2, base450), c (r3 vad250) |

Our own code is not the bottleneck: client time e ≤ 0.3 ms, rule matching ≈ µs (`fast_rule_timer.js`), the POST round trip d ≈ 5–12 ms (posts-only run: emergency button 4.8 ms p50, rule POST 5.8 ms p50, 74 ms p95; `latency_trace/posts/summary.json`). What the user waits for is **VAD silence + ASR + (model tools only) the model**.

**VAD wait vs configured silence** (server_vad, r2, wall a p50): silence 250 → 979, 350 → 1131, 450 → 1251 ms. Slope ≈ 1 ms per ms configured, **but a constant ≈ 730 ms remains** on top of the configured silence (server span minus our energy-gated voiced span = 690/784/908 ms at 250/350/450). I could not split that remainder (TTS tail below our RMS gate, 300 ms prefix padding handling, server VAD frame granularity, network) from the data; it is NOT attributed to anything specific.

**Harness caveat on `f` (async publish).** `latency_trace_client.js` only starts polling the compile-result file after the utterance loop ends (after `response.done`), so for the rule path `f` is bounded below by "model still answering" (in 64/64 r2 rule rows `f` is within 250 ms of model `tool_done − POST end`). `f` for rule rows (≈ 540–1500 ms) is therefore an **artifact, not publish time**, and `f` is excluded from "dominant" and from the user-visible ack. The real post-return publish cost was measured separately (R3-C: ≈ 17–22 ms in `lifecycle_skip_ab.py`, which polls immediately after the POST returns).

# Round 2 — rule-first routing, five promoted families, emergency endpoint (branch `feat/r2-speed`)

Everything here is offline (recorded real-ASR calls, unit tests) or a measurement against the real Realtime proxy. SC2 was not involved. **Every latency number in this section was measured on an overloaded machine** (load average 40 → 300 during the sweep, 28 → 245 during the ASR probe; see `docs/bench-results/latency_sweep.md` and `asr_words_probe.md`); p50 4.7 s here corresponds to ≈1.9 s on a quiet machine in the earlier run. Compare only inside one table.

## R2-A. What changed

| area | change |
|---|---|
| client (`electron/voice.js`, `voice_state.js`, new `electron/fast_rules.js`) | When the input transcription **completes** (`conversation.item.input_audio_transcription.completed`) the JS port of the deterministic matcher runs. On a hit the client immediately `POST /api/realtime/intent {transcript, fast:true, path:"rule"}`, then sends `response.cancel` for the model's in-flight response and ignores that response's later tool call (dedupe by turn/response id and `call_id`). No hit, a negation, a `fast_miss` answer or a failed request ⇒ the model's tool call runs as before (a call that arrives while the rule request is in flight is parked and released, never lost). Per-turn latency is reported as `{speech_end_to_decision, decision_to_publish, path: rule|model}` (the old `speech_end_to_tool_call` / `tool_call_to_publish` keys are kept for the HUD readout). `getPrefs().fastRules === false` switches it off. |

**Transcription hints.** The proxy accepts `language` and `prompt` and **echoes them back in `session.updated`** (verified live via the minted-secret path: `{"model":"gpt-4o-mini-transcribe","language":"ko","prompt":"StarCraft II 테란 …"}`), so they are not silently dropped. They did not improve ASR fidelity in this sample (exact-text transcripts at rep 0: 72 % without vs 71 % with hints; fast-path hit rate 35 % vs 36 %) and the hinted runs were slower at p95. Therefore they ship **opt-in** (`VOI_REALTIME_TRANSCRIBE_HINTS=1`, or explicit `VOI_REALTIME_TRANSCRIBE_LANGUAGE` / `_PROMPT`), with the graceful-degradation ladder (hinted → plain transcription → no transcription; text output → audio output) and unit tests. ## 2. Selection rule and what it picked
Eligible = unsafe ≤ 2 %, error rate ≤ 5 %, p95 ≤ tier budget (emergency 3 s, micro 5 s, others 8 s); best = max `sem`; tie band 2 pp; pick min p95 (then p50).
Candidates = deployable pipelines only (Realtime alone and cascades; transcript-only text models need an ASR and appear only inside cascades). Same rule as before.
Result: best = 89.1 % (A); tied within 2 pp: A, ext-shipfast→RT few-shot (88.3), D veto (87.5), B (87.3); the rule picks min p95 → **A**. A beats B by only 1.8 pp (not
significant; the gain is almost entirely `micro`: 90.9 vs 85.9), but it is also strictly faster for the 41 % of utterances it answers on its own, and it removes a model call for them.

Per-tier selections (budgeted): micro `ext→RT shipped` 93.9 %, emergency `ext→RT few-shot` 97.1 %, operation RT few-shot 87.6 %, macro `ext→RT few-shot` 90.1 %,
adversarial: **none eligible** — every deployable pipeline has 2.2 % unsafe on adversarial rows (> 2 % cap; the single injection row adv-030); the best by accuracy is D at 91.4 %. The per-tier winners are a diagnostic, not routes — a router cannot know the tier before the model decides.

**Few-shot vs shipped prompt (paired, same audio):** 417 vs 406 correct of 477 pairs (29 only-few-shot, 18 only-shipped; sign test p ≈ 0.14) → few-shot helps by +2.3 pp, **not
statistically established**; it clearly helps macro (+10 pp) and hurts micro (−4 pp) in this sample.

## 4. Ephemeral secret path, 429 and latency (claim 3)
Used `POST /realtime/client_secrets` with exactly `realtime_intent._session_body` (instructions and tool swapped for the few-shot variant), 3-try exponential backoff on 429, 60 s circuit breaker, then — **only when the ladder is exhausted** — long-lived key + identical `session.update`.
* 957 Realtime calls total (the two shipped configs; 52 of them came from the first launch with an 8-try mint ladder and no fallback, all minted without 429). **225 HTTP 429 responses** (`realtime_client_secret_capacity_exhausted`), **75 calls hit ≥ 1 429**.
* **Only 240 / 957 (25 %) completed through a minted ephemeral secret; 717 (75 %) used the long-lived-key fallback** because the proxy's secret capacity stayed exhausted for minutes at a time (a probe of 18 sequential mints over 103 s: 18 × 429).
  So the ephemeral path is **not verified for 75 % of the calls**; it works when capacity exists (mint p50 0.48 s, p95 1.44 s). This is an infrastructure limit of the proxy, not of the code, but `/api/realtime/session` will return 429 to the UI in such windows — the UI needs a retry/backoff + visible "voice unavailable" state.
* **Latency does not include secret minting** (the app mints before the user speaks). Measured effect of the auth path on the latency window: few-shot minted p50/p95 1.97/2.54 s (n = 124) vs fallback 1.95/2.79 s (n = 355): no difference.
* Zero realtime errors/timeouts after retries; 45 / 479 few-shot calls (9.4 %) returned **no input-transcription within the 10 s grace window after the tool call** — a real ASR dependency for every text step (see §6).

# Round 6 — "draw a route on the minimap": sketch -> route benchmark (branch `feat/r6-bench`)

What it measures: the user holds ⌃⌥ and draws on the SC2 minimap; `starcraft_commander.route_sketch.interpret_sketch(req, world, vlm=...)` must turn the strokes (+ what was said) into an ordered route and a final move/attack for a squad, or ask once (Korean), refuse, or do nothing. Geometry (minimap frame -> world) is deterministic from the strokes; the VLM only decides semantics (which stroke is a path / target circle / avoid mark / squad circle, order, move vs attack) and every point it could add must lie on a stroke (validator). Rule #1 metric: **unsafe = 0** (executing when gold is ask/refuse/none, or executing a point that is not on the user's strokes).

## R6-A. Corpus (`scripts/bench/route_corpus.jsonl`, 158 rows, 267 strokes, regenerated byte-identically by `route_corpus.py`; test `test_route_bench.py`)

Synthetic minimaps (`route_world.py`, PIL): square frame, playable area letterboxed (aspect preserving, centered), cliff blobs, own (green) and enemy (red) dots, own/enemy/neutral base markers; 4 layouts, 128-184 unit maps. Strokes are synthesised from the gold geometry with human traits (ease in/out + speed bursts, 24 ms sampling, tremor, slow wobble, end overshoot, 3-8% radius wobble and open/overlapping circles). Gold (ordered intermediate waypoints, final action + point, squad count/type, avoid zones, expected kind) is computed from the world BEFORE the strokes are drawn, never by a model.

## R6-B. Metrics (`route_scoring.py`, unit-tested in `test_route_bench.py`)

- kind accuracy (strict) and **lenient** kind accuracy (also accepts `ask` on the 21 rows whose squad is only implied by where the path starts: asking "which squad?" is safe there, executing is the gold).
- waypoint error in world units (wu): every gold route point (bend corners + final) is matched to a predicted point with an ORDER-PRESERVING assignment (DP, non-decreasing indices), mean and p95 over all matched gold points of rows where the system executed; order ok = final within 12 wu and bends visited in order (rows with >= 2 gold route points); final action ok; squad ok (count equal, and the type named when gold names one).
- **unsafe**: executed although gold is ask/refuse/none, or any executed route point farther than 6 wu from every stroke and not inside a loop the user drew (circle interior counts as drawn). Unanswered (exception / bad kind) is a miss, never unsafe.
- latency (one `interpret_sketch` call incl. the VLM request, rendered PNG excluded) p50/p95, tokens (proxy-reported total per call).

## R6-D. Selection and default

Rule: among variants with unsafe = 0, best kind accuracy, then lowest waypoint p95, tie band 2 pp on kind accuracy -> lower p50 latency.
All six have unsafe = 0. Best kind accuracy = gemini-3.8-flash-high 0.899 (lenient 0.918); the next best (gpt-6-sol 0.810, gemini-3-flash 0.794) are 9-10 pp lower, outside the 2 pp tie band, so the faster gemini-3-flash does not tie.
**Chosen default: `VOI_ROUTE_VLM_MODEL=gemini-3.8-flash-high`.** Cost: p50 5.8 s / p95 11.5 s per sketch at load ~12 (gemini-3-flash 3.5 / 5.6 s; the user keeps the chord down while drawing and the plan is announced before it runs, so a few seconds are tolerable, but this is the slowest of the practical options). If latency matters more than 10 pp of accuracy, gemini-3-flash is the safe fallback (also unsafe 0, but it asks "which squad?"/"which target?" much more often).

## R6-F. NOT measured

- Real SC2 minimap pixels: images are a synthetic PIL rendering (flat terrain, dots, base squares). A real minimap's colours, fog of war, creep, camera box, unit-type clutter and size are not here; VLM semantics may degrade on it. SC2 is not installed on this machine.
- Real human drawings: strokes are synthesised (jitter, overshoot, uneven speed, wobbly circles). Real strokes from a mouse/trackpad under pressure have different corner rounding, double-backs, accidental taps and drawing-while-talking timing.
- The letterbox frame -> world mapping ("SC2 draws the playable area fitted and centered in the square minimap frame") is an assumption: the benchmark implements it independently of the backend (same assumption, two copies) and never checks it against a live game. Calibration offset is 0 here.
- Live game: no order was issued to SC2, no unit moved along a route, no agent cursor was rendered; `squad` is the resolved cluster/units from the synthetic world, not real unit tags in a running game. Voice transcripts are typed text (no ASR). Squad naming covers only `<unit> N기` / `<unit>만`.
- The corpus doubled as the development set for three guard rounds (see C); a fresh seed set was not generated after the last fix. Variance: 2 reps at temperature 0, n per cell 16-48, so single-category differences below ~10 pp are not significant. Latency was measured on a shared, heavily loaded machine (load average 9-127).
